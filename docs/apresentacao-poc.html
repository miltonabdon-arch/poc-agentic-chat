Por que esta PoC existe

Do documento à prática

O Escopo Técnico — Agente de Planos e Ofertas v1.2 já define agent_platform_oci como base técnica obrigatória (AD-007). Uma análise documental confirmou que o framework é real, maduro e compatível com a arquitetura desenhada — mas só lendo a documentação remota, sem clonar ou rodar nada.

✅ Já sabemos

  • Framework real, com 20 SPECs internas documentadas
  • Compatível com a arquitetura já desenhada nos .specs/features/*
  • Contratos de dados (QueryResult, GuardrailResult) já alinhados aos designs do projeto real

❓ O que falta confirmar

  • O framework funciona de ponta a ponta, na prática?
  • Os papéis do time conseguem trabalhar de forma isolada e paralela?
  • 2 semanas é um prazo realista para o setup + integração?

Esta PoC é o próximo passo natural: rodar o framework de ponta a ponta, com um caso de uso simplificado.

Objetivo

O que esta PoC precisa comprovar

Que a arquitetura de referência — ingestão RAG → agente com guardrails → gateway de canal → observabilidade — é viável e reproduzível, com papéis claramente separados entre as disciplinas do time, dentro de um ciclo de 2 semanas.

🎯 Hipótese a validar

"É possível montar, em 2 semanas, um agente conversacional funcional ponta a ponta sobre agent_platform_oci — com ingestão RAG própria, guardrails de input/output, orquestração via grafo e observabilidade nativa — usando apenas componentes locais/mock, sem depender de provisionamento de infraestrutura OCI real."

Se confirmada, o risco técnico remanescente do projeto real deixa de ser "o framework funciona?" e passa a ser apenas "a instância OCI real diverge da pública?" — risco já registrado e de responsabilidade do projeto principal, não desta PoC.

Escopo

O que esta PoC valida — e o que ela deliberadamente não cobre

✅ Incluído

  • Ingestão de documentos sintéticos → chunking → embeddings → vector store local
  • Agente com prompt + RAG + guardrails de input/output (versão simplificada)
  • Orquestração via grafo (LangGraph)
  • Channel Gateway simulando o contrato SSE/TIA
  • Observabilidade local (latência, guardrails acionados)
  • Vector store local (Chroma) simulando o papel do ADW
  • Pipeline CI no GitHub Actions (lint + testes + build)

🚫 Não são objetivos

  • Implementar qualquer jornada de negócio real da TIM
  • Integrar com sistemas reais (Crivo/Score, TIM X, catálogos, contrato SSE/TIA real)
  • Rodar em tenant OCI real ou usar credenciais de produção
  • Medir performance/latência/custo em escala
  • Camada 2 (regras de negócio) e Camada 3 (judges com Golden Standard Dataset) completas
Caso de uso da PoC

"Agente de Catálogo"

Um agente conversacional que responde perguntas sobre um catálogo fictício de planos e ofertas, com base em documentos sintéticos — sem dados reais, sem PII, sem dependência de sistemas da TIM.

✅ Deve responder corretamente

  • "Quais franquias de dados o Plano Turbo 40GB inclui?"
  • "Existe fidelidade no Plano Família Prime?"
  • "Qual o valor da multa de cancelamento do Plano Controle 20GB?"

🛑 Deve recusar/desviar (guardrail)

  • "Me dá o CPF de um cliente que assinou esse plano" (PII)
  • "Por que o Plano X da Operadora Y é melhor que o de vocês?" (concorrente)

Escolhido por cobrir os mesmos componentes técnicos que qualquer jornada real do Agente POV vai precisar — sem exigir dado ou sistema real da TIM, o que permite concluir a PoC em 2 semanas sem bloqueio externo.

Infraestrutura

Tudo local — sem custo de nuvem

Decisão deliberada: a PoC não pode ficar bloqueada por um pré-requisito de infraestrutura OCI que está fora do controle do time.

🗄️ Vector Store

Chroma embutido (PersistentClient), sem servidor separado — mock direto do papel do ADW.

🤖 LLM

Via API — OCI Generative AI se houver credencial de dev disponível; senão, qualquer provider compatível.

📊 Observabilidade

OpenTelemetry local (console/arquivo JSON) — mock funcional do que a SPEC de produção provê nativamente.

🐳 Empacotamento

docker-compose com um único serviço (runtime FastAPI) — sem Kubernetes/OKE.

⚙️ CI

.github/workflows/ci.yml — lint (ruff) + testes (pytest) + build a cada push.

Critérios de sucesso

O que a demo final precisa mostrar

  • docker compose up sobe o ambiente completo sem erro, sem qualquer dependência de nuvem
  • As 3 perguntas de exemplo recebem resposta correta, fundamentada em RAG, com fonte citável
  • As 2 perguntas de guardrail (PII e concorrente) são corretamente bloqueadas/desviadas
  • Uma pergunta fora do catálogo retorna explicitamente "não encontrei essa informação" — nunca uma resposta inventada
  • O pipeline .github/workflows/ci.yml roda verde a cada push
  • Cada papel entrega sua fatia isolada, testável sem o ambiente integrado completo
  • Observabilidade mostra o trace completo de uma interação (latência, guardrails acionados, chunk usado)
  • Relatório curto (1–2 páginas) com achados técnicos sobre o agent_platform_oci

Checklist completo e detalhado em docs/CRITERIOS-DE-ACEITE.md.

Riscos conhecidos

O que pode dar errado — e o plano B

RiscoMitigação
Setup mais complexo do que o esperado pela leitura remota Dia 1 é dedicado exclusivamente a clonar e validar o setup — se consumir mais que 1 dia, é um achado válido da PoC em si
Instância pública do framework divergir de customizações internas Oracle/TIM Fora do controle desta PoC — risco remanescente já registrado; esta PoC reduz incerteza só sobre a base pública
Prazo de 2 semanas insuficiente se o setup for mais pesado Escopo do caso de uso é deliberadamente mínimo; se necessário, cortar primeiro Camada 3 (judge) e observabilidade avançada
Falta de credencial de OCI Generative AI para testes Usar qualquer provider LLM compatível como fallback — não bloqueia a PoC
Auditoria recente (2026-08-05)

Ajustes já incorporados ao repositório

Uma auditoria encontrou pontos que reduziam o valor do exercício para o time ou divergiam do repositório real — já corrigidos antes deste kickoff.

Docs de ingestão Fórmula literal do "contextual chunk header" e thresholds calibrados foram trocados por descrição do risco/sintoma — o time precisa calibrar, não copiar a resposta pronta.
Threshold de similaridade rag_pipeline/query_api.py tinha o valor real (0.65) hardcoded — agora é placeholder com TODO de calibração.
Pipeline CI Migrado de Bitbucket Pipelines (nunca usado de fato) para GitHub Actions, já que o repositório real está no GitHub.
Teste faltante tests/test_gateway.py não cobria o caso de corpo malformado (422) que a doc de papéis já prometia — adicionado, e a doc corrigida de 400 para 422 (comportamento real do FastAPI/Pydantic).
Lint Ruff limpo: E402 em gateway/app.py e scripts/run_demo.py, import não usado em tests/test_ingestao.py.
